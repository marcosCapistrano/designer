SELF-REVIEW NOTES (judgment calls where the brief is silent; please confirm)
1. A stale build.task (lower id, or same id with updatedAt older than current) is ignored as a whole message, including its
   running flag. Only an accepted task sets running. Reason: a stale running=false must not clear the running state of the
   newer task that is actually in progress. The brief says "build.task sets running from the message"; I read this as
   "for an accepted task".
2. applyState uses the same replacement rule for the snapshot's task (a null snapshot task keeps the current task). This stops a
   late snapshot from regressing the view to an older task after a newer build.task has already arrived. applyState sets
   running from the snapshot unconditionally, as the brief says.
3. Duplicate message ids: the incoming row overwrites the stored one. Message rows are immutable on the server, so this only
   matters for the ordering race above.
4. parseHash: a path with more than two segments after '#/apps/' is treated as "anything else" -> apps. A trailing slash
   ('#/apps/x/') yields area '' -> build.
5. summarizeTask: the running rule (step 2) applies to every status, so a running queued or merged task gets
   'Wait for Claude to finish.' as its hint. This follows the brief's order literally.
6. applyServerMsg returns v itself for other apps, stale tasks and non-Build messages (render.ready, pong).
7. No Date, Math.random or I/O. Inputs are not mutated (mergeMessages builds a new Map and array).
