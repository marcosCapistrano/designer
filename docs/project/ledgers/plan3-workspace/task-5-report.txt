1. WHAT WAS IMPLEMENTED
-----------------------
apps/server/src/auth/passphrase.ts
  - SCRYPT_PARAMS = { N: 16384, r: 8, p: 1, keylen: 32 } (as const)
  - MIN_PASSPHRASE_LENGTH = 12
  - hashPassphrase(passphrase, salt = randomBytes(16)) returns
    `scrypt:16384:8:1:<salt base64url>:<key base64url>` (no '$').
    Uses scryptSync with maxmem 64 MiB.
  - verifyPassphrase(passphrase, stored) parses the six ':' fields, requires
    the scheme 'scrypt' and decimal N/r/p, requires base64url salt and key,
    derives a key of the stored key's length, and compares with
    timingSafeEqual. Any malformed input returns false. The whole body is in
    try/catch, so it never throws.

apps/server/src/auth/limiter.ts
  - LimiterOptions { maxFailures = 5, windowMs = 900_000, lockMs = 900_000 }
  - class LoginLimiter: blocked(now) is now < lockedUntil.
    fail(now) drops failures older than windowMs, records now, and at
    maxFailures sets lockedUntil = now + lockMs and clears the failures.
    reset() clears the failures.
  - Time is passed in as a parameter. Nothing reads the clock.

apps/server/src/auth/hash-cli.ts
  - Reads all of stdin, strips exactly one trailing "\r\n" or "\n".
  - If the result is shorter than 12 characters, it writes
    "Passphrase must be at least 12 characters\n" to stderr and exits 1.
    The passphrase is never echoed.
  - Otherwise it writes hashPassphrase(input) + "\n" to stdout.
  - Wired to the existing `hash-passphrase` script in apps/server/package.json
    (added by Task 3). package.json was not edited.

6. SELF-REVIEW NOTES
--------------------
- The brief's values are used verbatim: the scrypt parameters, the 12-character
  minimum, 5 failures, the 900_000 ms window and lock, and the exact stderr copy.
- verifyPassphrase is generic over the stored key length, as the brief says.
  Stored hashes come from the server's credential or environment, never from
  request input, so this is safe here.
- The CLI reads stdin with for-await, so it works for pipes and files. On Linux
  stderr to a pipe is synchronous, so the message is flushed before process.exit(1).
- Error paths never include the input passphrase. The top-level catch only
  prints error.message, and scrypt errors do not contain the input.
- Intentional I/O: hash-cli.ts does stdin and stdout I/O and passphrase.ts uses
  randomBytes. The brief requires both, so this is a deliberate exception to the
  "no I/O in src" convention and not an oversight.

7. CONCERNS
-----------
a) reset() clears recorded failures only. It does NOT lift an active lock
   (lockedUntil is untouched). The brief says "reset clears failures" and the
   interface has no further comment, so I followed it literally. If the
   controller intends reset() to also end a lockout, that is a one-line change.
b) The login route (a later task) must check blocked(now) before calling
   verifyPassphrase, and call reset() after a successful login. fail(now) still
   records failures while locked, so this ordering is the caller's job.
c) Running hash-cli.ts interactively on a TTY echoes the typed passphrase, because
   it does not disable terminal echo. The brief's usage is piped stdin, so I did
   not add termios handling.
