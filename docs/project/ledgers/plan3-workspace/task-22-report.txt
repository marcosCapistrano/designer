SELF-REVIEW NOTES

1. Two tests beyond the brief's list (19 total, brief said 17):
   - "kick pings an open socket without reconnecting" (the brief specifies the open-branch behavior of kick but no test for it).
   - "connect after close starts the backoff fresh" (connect() resets attempt, which the brief does not state; close() does not).
2. Behavior choices not spelled out in the brief:
   - kick() does nothing before connect() or after close(), so a visibility-change kick cannot revive a closed client.
   - kick() while status is 'connecting' abandons the in-flight socket (close() on it, its late events ignored) and opens a new one, matching "otherwise reconnect now".
   - connect() is a no-op while already running.
   - onStatus does not emit the current status on subscribe; get status is the way to read it. Status events are deduplicated (same status twice is not re-emitted).
   - On pong timeout the client calls socket.close() and immediately treats the socket as dropped, instead of waiting for the browser's close event (which can be slow on a dead TCP connection). With fake sockets both paths converge on the same state.
3. Idempotent socket handling: abandon() and dropped() both ignore sockets that are no longer the current one, so a close event arriving after replacement or after a pong timeout does nothing.
4. Clock: `now` defaults to Date.now, following apps/client/src/canvas/loader.ts. The "no Date in src" convention in the implementer instructions could not be applied literally here because the brief requires a now() option and the ping timestamp.
5. Bundle: net/ is not imported by main.tsx yet. The only runtime import is parseServerMsg from the root '@hub/protocol' index, which does not pull in zod.

CONCERNS

A. parseServerMsg checks only the `type` tag (as noted in the dispatch). A message with a known type but a malformed payload is still forwarded. Example: render.ready without `manifest` reaches ServerTileSource and calls onManifest(undefined); build.task without `task` reaches listeners. The brief says "invalid ones are dropped", which this implementation only satisfies for unknown types and non-JSON. Payload validation would need either a change in packages/protocol (outside this task's files) or per-type checks in the client. I did not add either; the controller should decide.

B. ApiClient.apps() assumes GET /api/apps returns AppSummary[] directly (the brief's signature). The plan does not pin the body shape for the apps list, unlike the build routes (buildState returns BuildState directly, sendBuild/merge/closeTask return {task}, stopBuild returns {stopped}). The server's apps route (Task 19 area, not present in this worktree) must return a bare array or this client must change.
